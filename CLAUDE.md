# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Recipe Hub — a mobile app (iOS/Android) for capturing and structuring recipes (Instagram share import, photo capture, AI structuring via the Claude API). Phase roadmap: Phase 0 socle → Phase 1 manual CRUD → Phase 2 Instagram import → Phase 3 photo import → Phase 4 social → Phase 5 intelligent.

**Current state: Phase 1 (manual CRUD) closed (2026-09-10), Phase 2 (Instagram import) in progress.** Auth (JWT), recipe CRUD, and photo upload work end-to-end (mobile ↔ API ↔ Postgres/MinIO) and have been through a manual testing pass — see `NOTES.md` ("Traité") and `CONCEPTION.md` section 8 for what was covered, including a same-day fix for per-user scoping of the ingredient/tag vocabulary (found via multi-account testing). Phase 2 slice 1 (scraping + Claude structuring, manual-URL entry point) is implemented, and it and the follow-up UI work (collections, Profile tab) were fully validated on device on 2026-09-29 — see the Phase 2 paragraph below. Later on 2026-09-29 the Instagram scraper was rewritten (plain fetch + the post JSON embedded in the page — ~10s → ~1.5s, real Reel covers; the headless browser was then removed entirely), and the import became a single server call (`POST /imports/instagram`: scrape + Claude, photo sent to Claude only when the caption is too short) with time-based progress messages while waiting — all validated on device the same day. **Next: Phase 2 slice 2** (native OS share-intent via `expo-share-intent` + a dev client — not started yet). A friendlier import waiting screen is noted as a to-design idea in `NOTES.md`.

## Repo structure

npm workspaces monorepo:

```
apps/api/       Fastify + TypeScript + Prisma backend
apps/mobile/    Expo + TypeScript + React Navigation mobile app
```

The two apps share no code today (no `packages/` in use yet) beyond the root `npm install`.

## Commands

Run from the repo root unless noted.

```bash
npm install                       # installs both workspaces
docker compose up -d              # starts postgres (:5432) + minio (:9000/:9001) — required before running the API
npm run dev:api                   # starts the API (tsx watch) on :3000
npm run dev:mobile                # starts Expo (Metro) for the mobile app
```

Prisma (run from `apps/api`, or via the root scripts):

```bash
npx prisma migrate dev --name <name>   # create + apply a migration after editing schema.prisma
npx prisma generate                    # regenerate the Prisma Client (also runs automatically after migrate)
npx prisma studio                      # inspect the DB visually
```

Typecheck (no test suite exists yet in either app):

```bash
cd apps/api && npx tsc --noEmit
cd apps/mobile && npx tsc --noEmit
```

Instagram import smoke test (hits Instagram for real — checks the scraper still works on 6 reference posts; run it when public posts start landing on the "restricted or deleted" manual form):

```bash
npm run check:instagram
```

Claude structuring benchmark (⚠ calls the Claude API for real, ~$0.30 per run on `ANTHROPIC_API_KEY` — 3 reference posts × 4 model/photo configurations × 2 runs; timings printed, drafts written to the gitignored `apps/api/scripts/bench-structure-results.json` for a side-by-side quality check):

```bash
npm run bench:structure
```

Health check once the API is running:

```bash
curl http://localhost:3000/health      # liveness only
curl http://localhost:3000/health/db   # round-trips through Prisma to confirm DB connectivity
```

## Architecture

**Request flow**: mobile app → HTTP/JSON → Fastify API → Prisma Client → PostgreSQL. Postgres and MinIO run in Docker (`docker-compose.yml`); the API and mobile app run directly on the host (not containerized) for fast reload during dev — there is no Docker image for the API yet, that's a deployment-time concern (`caddy` + prod compose file, not yet created).

**`apps/api`**: `src/server.ts` boots a Fastify instance (`src/app.ts`) on `0.0.0.0` (not just `localhost`, so a physical phone on the LAN can reach it). Routes are registered as Fastify plugins under `src/routes/`: `health.ts`, `auth.ts` (`POST /auth/register`, `POST /auth/login`, `GET /auth/me`, backed by `@fastify/jwt` + `bcryptjs`), `recipes.ts` (full CRUD, scoped to `req.user.userId` on every query, plus `GET/POST /tags` and `DELETE /tags/:id` for the user's own collections — see the Phase 2 paragraph below), `imports.ts` (Phase 2 — see below). `src/lib/prisma.ts` exports a single shared `PrismaClient` instance. `@fastify/cors` is registered with `origin: true` — required because Expo's web target and any browser-based testing hit the API cross-origin; native Expo Go/device builds aren't subject to CORS but the plugin is harmless for them. `@fastify/multipart` (`attachFieldsToBody: true`) parses recipe create/update requests, which are sent as multipart so a photo can ride along with the JSON-ish fields; `src/lib/minio.ts` uploads that photo to MinIO and recipes are served back through an authenticated proxy endpoint (`GET /recipes/:id/photo`) rather than exposing MinIO URLs directly.

**Prisma schema** (`apps/api/prisma/schema.prisma`): six models — `User`, `Recipe`, `Ingredient`, `RecipeIngredient` (join table with a free-text `quantity`, e.g. `"200g"`, plus a nullable `section`, e.g. `"Pour la pâte"` — lets the same ingredient appear more than once in a recipe with a different quantity per part, added 2026-09-11 after a real recipe with butter in both the dough and the cream crashed the save; unique on `(recipeId, ingredientId, section)`, with app-level dedup in `recipes.ts` as the real guard since Postgres treats two `NULL` sections as distinct; plus an `Int position` (added 2026-09-29, migration `20260929120000_add_recipe_ingredient_position`) = the ingredient's index in the submitted list, which `recipes.ts` writes on create/update and sorts by on read — before it, rows came back in arbitrary DB order, shuffling ingredients and interleaving sections; rows saved earlier all have `0`. On mobile, `groupBySection` (`src/lib/ingredients.ts`) gathers each section's items together — used for rendering on `RecipeDetailScreen` and on load in `RecipeEditScreen` — so a section title shows only once even for those older rows), `Tag`, `RecipeTag` (join table). `Recipe.steps` is a `Json` array of strings rather than a normalized steps table — deliberately minimal, revisit only if step-level metadata is needed. `Recipe.photoKey` stores the MinIO object key (nullable). `Recipe.source` (nullable free-text string, added 2026-09-10) records where a recipe came from — an Instagram/web link, a book, a person's name — deliberately untyped (no enum); the mobile detail screen renders it, when it looks like a URL, as a tappable "Voir la recette originale" chip (icon + label, `sourceLinkRow` in `RecipeDetailScreen.tsx`, added 2026-09-18) rather than the raw URL — a plain non-URL source (book, person) still renders as plain text. `Recipe.visibility` (`PRIVATE`/`PUBLIC`, default `PRIVATE`) exists now to support Phase 4 social sharing without a later migration. Account model is single-user (mono-utilisateur) — no group/family table. `Ingredient` and `Tag` each carry a `normalized` column (distinct from the display `name`) so find-or-create on recipe save is case-insensitive (`normalizeWord` in `recipes.ts`: `trim().toLowerCase()`) — added in migration `20260908104606_normalize_ingredient_tag_names` after duplicate rows showed up for things like "tomate"/"Tomate". It was briefly also plural-insensitive (stripping a trailing "s"), but that was dropped 2026-09-10: singular/plural carries real meaning (quantity agreement, e.g. "1 tomate" vs "4 tomates"), so "tomate" and "tomates" are now kept as distinct rows on purpose. Both models also carry a `userId` (FK to `User`, `onDelete: Cascade`) — added 2026-09-10 (migration `20260910120000_scope_ingredients_tags_by_user`) after testing with a second account showed the vocabulary was global across every user rather than private per account; the unique constraint is now `(userId, normalized)` rather than `normalized` alone, and the find-or-create upserts in `recipes.ts` key on that compound field (`userId_normalized`).

**`apps/mobile`**: `App.tsx` renders `src/navigation/RootNavigator.tsx` (React Navigation native-stack) with screens — `AuthScreen`, `RecipeListScreen`, `RecipeDetailScreen`, `RecipeEditScreen`, `ImportScreen`, `ProfileScreen` (added 2026-09-15, minimal — account email + logout, see `NOTES.md`) — all wired to the API, not stubs. `src/context/AuthContext.tsx` holds the JWT and persists it via `src/lib/storage.ts` (`expo-secure-store`, falling back to `localStorage` on the web build). `src/lib/api.ts` wraps `fetch` against `EXPO_PUBLIC_API_URL` (must be the dev machine's LAN IP when testing on a physical device — `localhost` from a phone means the phone itself) and builds multipart `FormData` for recipe create/update. Photo capture/selection in `RecipeEditScreen` goes through `expo-image-picker` (camera + library choice), whose iOS/Android permission strings are declared via the `expo-image-picker` config plugin in `app.json`. `metro.config.js` extends Metro's `watchFolders`/`resolver.nodeModulesPaths` to the monorepo root — required for Metro to resolve npm-workspaces-hoisted dependencies; without it the bundler can't find packages hoisted above `apps/mobile/node_modules`.

**Visual identity ("Tambo")**: the app's working name is **Tambo** (displayed in-app only — `app.json` name/slug, `package.json`, and the repo name are still `recipehub`/unchanged, a deliberate scoping decision from 2026-09-10). `src/lib/theme.ts` centralizes colors, border radii, and font tokens (`fonts.serif*` → Fraunces, `fonts.sans*` → Urbanist as of 2026-09-18 (was Inter), loaded via `@expo-google-fonts/{fraunces,urbanist}` and `useFonts` in `App.tsx`, which also holds the splash screen with `expo-splash-screen` until fonts are ready) plus `NO_PHOTO_EMOJI` (🍽️, still used as the no-photo placeholder on `RecipeDetailScreen`; superseded on `RecipeListScreen`'s recipe cards and collection mosaics by a `MaterialCommunityIcons name="food-variant"` icon on a colored (`colors.ochre`) background, 2026-09-18) — that placeholder background and the real photo were briefly the same container, so a reduced-opacity photo let the ochre bleed through as a tint; split into dedicated `cardPhotoPlaceholder`/`mosaicPlaceholder` styles applied only when there's no photo (2026-09-18 fix). `src/components/Wordmark.tsx` renders the "Tambo." wordmark (Fraunces, terracotta-dot) reused on `AuthScreen` and `RecipeListScreen`, with a per-screen `size` prop (36 on `AuthScreen`, 34 on `RecipeListScreen`). `RecipeListScreen` has a custom header (native React Navigation header hidden for this screen) with a client-side search filter and a Recettes/Collections toggle (underlined text tabs since 2026-09-18, no more pill background) — Collections groups recipes by tag client-side (`tags` is returned on `GET /recipes`), while the list of collections itself comes from `GET /tags` so empty ones show too, sorted alphabetically, rendered as an adaptive photo mosaïque (1/2/3/4+ recipes). It also has a bottom icon bar (Collections/Profil/Partager, icons from `@expo/vector-icons` — `Feather` plus `MaterialCommunityIcons` for food-specific glyphs, cream background/terracotta icons as of 2026-09-18 (was white/charcoal)) with Collections and Profil wired up (Profil added 2026-09-15, navigates to the new `ProfileScreen`); Partager still has no screen behind it. Since 2026-09-26 the bar is a shared `src/components/BottomNav.tsx` (`active: 'collections' | 'profile'`) rendered on both `RecipeListScreen` and `ProfileScreen`: the current screen's icon is filled, the others outlined, all `Ionicons` pairs (`book`/`book-outline`, `person`/`person-outline`, `share-social-outline`). `ProfileScreen` is treated as a tab-like destination, not a pushed screen — no back button, no swipe-back, no transition animation (`RootNavigator.tsx`), and its Collections icon returns via `navigation.popTo('RecipeList')`. The recipe card in the "Recettes" grid shows photo (larger since 2026-09-18) + title + tag chips (re-added 2026-09-18 after being removed 2026-09-15, see `NOTES.md`) + a prep-time indicator when `prepTimeMin` is set, on a shadow-elevated card (no border) — recipes are sorted alphabetically like collections. The "+" button floats (`position: absolute`) above the list/mosaic rather than sitting in the normal layout flow (2026-09-18).

**Collection membership management (`RecipeListScreen`, 2026-09-18)**: opening an empty collection shows "Cette collection est vide pour l'instant." plus an "Ajouter une recette" CTA that opens `RecipeEdit` with the collection already selected (same draft-prefill mechanism the Instagram import flow uses). Once a collection is open (empty or not), the floating "+" button opens a 3-option menu instead of the generic one: "Sélectionner des recettes existantes" (a multi-select picker — tap to check/uncheck, header "Terminé" button batch-applies the tag via `getRecipe` + `updateRecipe` per recipe, since `PUT /recipes/:id` has no partial-update mode — filterable via the screen's existing search bar), "Importer depuis Instagram" (opens `ImportScreen` with a new `presetTag` route param, merged into whatever tags the scrape/Claude structuring or manual fallback produces), or "Ajouter une recette" (same prefilled-draft create as the empty-collection CTA). A collection also has its own "edit mode" (list icon next to the rename/delete icons, hidden when the collection is empty): each card gets a small remove badge (`handleRemoveFromCollection`) that un-tags the recipe immediately on tap, deliberately no multi-select step since removing from a collection doesn't touch the recipe itself. The floating "+" is hidden during both the picker and edit mode to avoid overlapping affordances.

**Phase 2 — Instagram import (slice 1, 2026-09-10)**: no native OS share-intent yet (that's slice 2 — needs `expo-share-intent` and a dev client build, since it requires native code Expo Go can't run). For now the entry point is manual: `RecipeListScreen`'s "+" button offers "Nouvelle recette" / "Importer depuis Instagram" / "Nouvelle collection" (`Alert.alert` — or, inside an open collection, the 3-option menu described in the Collection membership management paragraph), "Importer depuis Instagram" opening `ImportScreen` where the user pastes a post URL. `POST /imports/instagram` (2026-09-29, replaced `POST /imports/scrape` + a second structuring call from the phone) does the whole import server-side in one call: scrape with `apps/api/src/lib/instagramScraper.ts`, then structure with Claude — so the post's photo no longer travels server → phone → server as base64 just for Claude. It always replies `200` with `scraped: boolean` (+ `draft`, null if Claude failed — caption/photo are still returned for a manual retry) rather than erroring, since a failed scrape is an expected case the UI falls back on (edit the caption / add a photo manually). The photo is only sent to Claude when the caption is under 150 characters (`CAPTION_ENOUGH_CHARS`): a cover shows the dish, not the recipe, and measured with `npm run bench:structure` it barely changed the drafts while adding ~0.4s and 35-60% more input tokens. Scraping itself is best-effort and unofficial. **Since 2026-09-29 it's a plain `fetch` + the post's embedded JSON — no headless browser** (full history, measurements and the decisions in between in `NOTES.md`, last Phase 2 items): fetches the post page (URL cleaned down to its shortcode, dropping share-tracking params like `?stkn=`) with full browser navigation headers (`Accept`, `Accept-Language`, `Sec-Fetch-*` — with a User-Agent alone Instagram omits the post data, which is why the original 2026-09-10 plain-fetch version failed and a headless browser was used 2026-09-11 → 2026-09-29), then reads the post straight out of the JSON Instagram embeds in the initial HTML (`<script type="application/json">` blocks): finds the media object whose `code` is the URL's shortcode, takes `caption.text` (author's text with line breaks, no username/date prefix), the largest `image_versions2` candidate (a Reel's real author-chosen cover) or every `carousel_media` image (max 10), downloaded right away (signed, expiring URLs). ~1-1.5s. Returns `{ ok: true, post }` or `{ ok: false, reason }` (`bad-url`/`http-error`/`unavailable`/`no-image`). `unavailable` = the page came back without the post's data: a restricted post (author-limited or age-gated, only shown to logged-in users), a deleted post and an Instagram page change are indistinguishable from a plain fetch (verified 2026-09-29), so the route replies `scraped: false, reason: 'unavailable'` (other failures: `'bad-url'` for a non-Instagram link, `'failed'` for network/timeout/image issues). `ImportScreen` turns each case — plus a 400 "Lien invalide" and an unreachable server, told apart via the exported `ApiError` — into its own title + explanation card (`NOTICES`), e.g. "Ce post n'est pas accessible" → copy the caption by hand (2026-09-29, replaced a single unexplained "Récupération automatique impossible"). `POST /imports/structure` is the manual path (user-entered caption and/or photo — the photo is always sent there, it may be the recipe itself, e.g. a cookbook page) and has a 10 MB `bodyLimit` (Fastify's 1 MB default rejected a full-resolution photo with a 413). `puppeteer-core`, the Chromium dependency and the video-frame capture were removed on 2026-09-29 (the browser had only been kept to word the restricted-post message more precisely). `npm run check:instagram` (`apps/api/scripts/check-instagram.ts`) runs the scraper on 6 reference posts — the only way to tell an Instagram page change from restricted/deleted posts. Fragile by design, accepted risk, see `CONCEPTION.md` §1 — the manual fallback (edit caption / add photo) stays as the safety net. `apps/api/src/lib/claude.ts` wraps `@anthropic-ai/sdk` (`ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` env vars, default model `claude-sonnet-5`) and structures a recipe from caption text and/or a photo using a **forced tool call** (`tool_choice: { type: 'tool', name: 'record_recipe' }`, `strict: true`) rather than free-text JSON parsing, for reliable structured output — used by both `POST /imports/instagram` and `POST /imports/structure`; it logs every call (`[claude] <model>: <ms>, input/output tokens, photo sent or not`) — latency is dominated by output length (700-1,000 tokens, the whole recipe rewritten), and Sonnet 5 was kept over Haiku 4.5 on 2026-09-29 for fidelity (Haiku was ~1.7s faster but dropped units and invented a prep time; results in `NOTES.md`). While waiting, `ImportScreen` shows a progress message that changes over time (`useProgressMessage` + `IMPORT_PROGRESS`/`STRUCTURE_PROGRESS`: "Lecture du post Instagram…" → "L'IA lit la légende et structure la recette…" → …) — time-based on measured phase durations, since a single server call can't report its real phase (2026-09-29). `ImportScreen` gets the draft from the import call (or, on the manual path, from `/imports/structure`), then routes to `RecipeEditScreen` with `route.params.draft` (the structured recipe) and `route.params.source` (the pasted URL) pre-filling the form — same screen used for manual create, just with a non-empty starting snapshot for the unsaved-changes guard (`RecipeEditScreen`'s `beforeRemove` listener, prompts to save/discard when leaving with pending changes). Photos in the scrape response: `photo` (always set on success) is the default recipe photo — single photo, a Reel's cover, or a carousel's first image; `photoCandidates` are a carousel's images. `ImportScreen` carries both through to `RecipeEditScreen` (`route.params.photo`/`photoCandidates`), which preselects the photo and keeps the carousel images behind "Changer Photo" (tile picker) — the **user** picks, consistent with keeping recipe organization (and cover selection) user-driven rather than AI-decided. (Before 2026-09-29, Reels had no fetchable cover in the rendered page, so frames captured at 0% and 98% of the video were offered instead — see `NOTES.md` for that history.) `saveBase64PhotoToFile` (`apps/mobile/src/lib/photo.ts`) is the shared helper both screens use to turn a base64 photo/candidate into the real `file://` uri the multipart upload needs. No video/audio processing (transcription is a separate, later increment per `CONCEPTION.md` §6 — the scraper already sees the Reel's direct MP4 URL in `video_versions`, logged but unused for now, which will make that simpler). **Collections stay user-controlled, tag = collection** (decided 2026-09-14, refined same day — see `NOTES.md`): a collection is deliberately named by the user, like naming a photo album, not generated by the AI. `claude.ts` still receives the user's existing tags as context and prefers reusing them, but the mobile side enforces the actual rule — `RecipeEditScreen` waits for `GET /tags` to load, then pre-selects only draft tags that match the user's existing vocabulary (reusing isn't creating); a genuinely new tag Claude proposes is silently dropped rather than offered as a one-tap suggestion, since even an AI-originated suggestion isn't how a collection should get its name. At least one collection is now **required** to save a recipe (enforced both in `RecipeEditScreen`'s `handleSave` and server-side via `tagsSchema.min(1)` in `recipes.ts`) — typing a name that doesn't exist yet still creates it via the existing find-or-create upsert, exactly as before. Collections are also manageable independently of any recipe: `POST /tags` (create/find-or-create standalone) and `DELETE /tags/:id` (cascades to `RecipeTag` rows only — the recipes themselves are untouched, like removing an album doesn't delete its photos) back collection creation/deletion on `RecipeListScreen`'s Collections tab (reworked 2026-09-15, see `NOTES.md` — the earlier "Gérer les collections" toggle is gone: creation is now a "Nouvelle collection" option in the "+" button's menu, deletion a trash icon next to the "Collection : X ✕" chip shown once inside a filtered collection), which now sources its list from `GET /tags` (every collection, including ones with zero recipes yet) rather than deriving it purely from recipes' embedded tag names. Membership in an existing collection is also user-managed after the fact — adding recipes to one (existing-recipe picker, Instagram import with a preset tag, or a fresh recipe) and removing them (per-card badge in the collection's edit mode) — see the Collection membership management paragraph above.

**Known Expo SDK 57 gotcha**: Expo replaces the global `fetch`/`FormData` with its own WinterCG-flavored implementation by default, which does not support React Native's classic `{ uri, name, type }` FormData file part (throws `"Unsupported FormDataPart implementation"`). `apps/mobile/.env`/`.env.example` set `EXPO_PUBLIC_USE_RN_FETCH=1` to fall back to React Native's built-in `fetch`, which does support it. After changing this var, restart with `npx expo start -c` (cache clear) and do a full reload on device — a plain restart or fast refresh isn't enough since the env value is inlined at bundle time.

**Env files**: each app has its own `.env.example` (`apps/api`, `apps/mobile`) plus a root one for `docker-compose.yml`. Copy to `.env` locally; none of the `.env` files are committed. `apps/api/.env` needs `ANTHROPIC_API_KEY` (from [console.anthropic.com](https://console.anthropic.com), pay-as-you-go — separate product from a Claude.ai subscription) for the Phase 2 import endpoints to work; everything else works without it.
