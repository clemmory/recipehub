# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Recipe Hub — a mobile app (iOS/Android) for capturing and structuring recipes (Instagram share import, photo capture, AI structuring via the Claude API). Phase roadmap: Phase 0 socle → Phase 1 manual CRUD → Phase 2 Instagram import → Phase 3 photo import → Phase 4 social → Phase 5 intelligent.

**Current state: Phase 1 (manual CRUD) closed (2026-09-10), Phase 2 (Instagram import) in progress.** Auth (JWT), recipe CRUD, and photo upload work end-to-end (mobile ↔ API ↔ Postgres/MinIO) and have been through a manual testing pass — see `NOTES.md` ("Traité") and `CONCEPTION.md` section 8 for what was covered, including a same-day fix for per-user scoping of the ingredient/tag vocabulary (found via multi-account testing). Phase 2 slice 1 (scraping + Claude structuring, manual-URL entry point) is implemented — see the Phase 2 paragraph below; native OS share-intent (slice 2) is not started yet.

## Repo structure

npm workspaces monorepo:

```
apps/api/       Fastify + TypeScript + Prisma backend
apps/mobile/    Expo + TypeScript + React Navigation mobile app
```

The two apps share no code today (no `packages/` in use yet) beyond the root `npm install`.

## Commands

Run from the repo root unless noted.

```bash
npm install                       # installs both workspaces
docker compose up -d              # starts postgres (:5432) + minio (:9000/:9001) — required before running the API
npm run dev:api                   # starts the API (tsx watch) on :3000
npm run dev:mobile                # starts Expo (Metro) for the mobile app
```

Prisma (run from `apps/api`, or via the root scripts):

```bash
npx prisma migrate dev --name <name>   # create + apply a migration after editing schema.prisma
npx prisma generate                    # regenerate the Prisma Client (also runs automatically after migrate)
npx prisma studio                      # inspect the DB visually
```

Typecheck (no test suite exists yet in either app):

```bash
cd apps/api && npx tsc --noEmit
cd apps/mobile && npx tsc --noEmit
```

Health check once the API is running:

```bash
curl http://localhost:3000/health      # liveness only
curl http://localhost:3000/health/db   # round-trips through Prisma to confirm DB connectivity
```

## Architecture

**Request flow**: mobile app → HTTP/JSON → Fastify API → Prisma Client → PostgreSQL. Postgres and MinIO run in Docker (`docker-compose.yml`); the API and mobile app run directly on the host (not containerized) for fast reload during dev — there is no Docker image for the API yet, that's a deployment-time concern (`caddy` + prod compose file, not yet created).

**`apps/api`**: `src/server.ts` boots a Fastify instance (`src/app.ts`) on `0.0.0.0` (not just `localhost`, so a physical phone on the LAN can reach it). Routes are registered as Fastify plugins under `src/routes/`: `health.ts`, `auth.ts` (`POST /auth/register`, `POST /auth/login`, `GET /auth/me`, backed by `@fastify/jwt` + `bcryptjs`), `recipes.ts` (full CRUD, scoped to `req.user.userId` on every query, plus `GET/POST /tags` and `DELETE /tags/:id` for the user's own collections — see the Phase 2 paragraph below), `imports.ts` (Phase 2 — see below). `src/lib/prisma.ts` exports a single shared `PrismaClient` instance. `@fastify/cors` is registered with `origin: true` — required because Expo's web target and any browser-based testing hit the API cross-origin; native Expo Go/device builds aren't subject to CORS but the plugin is harmless for them. `@fastify/multipart` (`attachFieldsToBody: true`) parses recipe create/update requests, which are sent as multipart so a photo can ride along with the JSON-ish fields; `src/lib/minio.ts` uploads that photo to MinIO and recipes are served back through an authenticated proxy endpoint (`GET /recipes/:id/photo`) rather than exposing MinIO URLs directly.

**Prisma schema** (`apps/api/prisma/schema.prisma`): six models — `User`, `Recipe`, `Ingredient`, `RecipeIngredient` (join table with a free-text `quantity`, e.g. `"200g"`, plus a nullable `section`, e.g. `"Pour la pâte"` — lets the same ingredient appear more than once in a recipe with a different quantity per part, added 2026-09-11 after a real recipe with butter in both the dough and the cream crashed the save; unique on `(recipeId, ingredientId, section)`, with app-level dedup in `recipes.ts` as the real guard since Postgres treats two `NULL` sections as distinct), `Tag`, `RecipeTag` (join table). `Recipe.steps` is a `Json` array of strings rather than a normalized steps table — deliberately minimal, revisit only if step-level metadata is needed. `Recipe.photoKey` stores the MinIO object key (nullable). `Recipe.source` (nullable free-text string, added 2026-09-10) records where a recipe came from — an Instagram/web link, a book, a person's name — deliberately untyped (no enum); the mobile detail screen renders it, when it looks like a URL, as a tappable "Voir la recette originale" chip (icon + label, `sourceLinkRow` in `RecipeDetailScreen.tsx`, added 2026-09-18) rather than the raw URL — a plain non-URL source (book, person) still renders as plain text. `Recipe.visibility` (`PRIVATE`/`PUBLIC`, default `PRIVATE`) exists now to support Phase 4 social sharing without a later migration. Account model is single-user (mono-utilisateur) — no group/family table. `Ingredient` and `Tag` each carry a `normalized` column (distinct from the display `name`) so find-or-create on recipe save is case-insensitive (`normalizeWord` in `recipes.ts`: `trim().toLowerCase()`) — added in migration `20260908104606_normalize_ingredient_tag_names` after duplicate rows showed up for things like "tomate"/"Tomate". It was briefly also plural-insensitive (stripping a trailing "s"), but that was dropped 2026-09-10: singular/plural carries real meaning (quantity agreement, e.g. "1 tomate" vs "4 tomates"), so "tomate" and "tomates" are now kept as distinct rows on purpose. Both models also carry a `userId` (FK to `User`, `onDelete: Cascade`) — added 2026-09-10 (migration `20260910120000_scope_ingredients_tags_by_user`) after testing with a second account showed the vocabulary was global across every user rather than private per account; the unique constraint is now `(userId, normalized)` rather than `normalized` alone, and the find-or-create upserts in `recipes.ts` key on that compound field (`userId_normalized`).

**`apps/mobile`**: `App.tsx` renders `src/navigation/RootNavigator.tsx` (React Navigation native-stack) with screens — `AuthScreen`, `RecipeListScreen`, `RecipeDetailScreen`, `RecipeEditScreen`, `ImportScreen`, `ProfileScreen` (added 2026-09-15, minimal — account email + logout, see `NOTES.md`) — all wired to the API, not stubs. `src/context/AuthContext.tsx` holds the JWT and persists it via `src/lib/storage.ts` (`expo-secure-store`, falling back to `localStorage` on the web build). `src/lib/api.ts` wraps `fetch` against `EXPO_PUBLIC_API_URL` (must be the dev machine's LAN IP when testing on a physical device — `localhost` from a phone means the phone itself) and builds multipart `FormData` for recipe create/update. Photo capture/selection in `RecipeEditScreen` goes through `expo-image-picker` (camera + library choice), whose iOS/Android permission strings are declared via the `expo-image-picker` config plugin in `app.json`. `metro.config.js` extends Metro's `watchFolders`/`resolver.nodeModulesPaths` to the monorepo root — required for Metro to resolve npm-workspaces-hoisted dependencies; without it the bundler can't find packages hoisted above `apps/mobile/node_modules`.

**Visual identity ("Tambo")**: the app's working name is **Tambo** (displayed in-app only — `app.json` name/slug, `package.json`, and the repo name are still `recipehub`/unchanged, a deliberate scoping decision from 2026-09-10). `src/lib/theme.ts` centralizes colors, border radii, and font tokens (`fonts.serif*` → Fraunces, `fonts.sans*` → Inter, loaded via `@expo-google-fonts/{fraunces,inter}` and `useFonts` in `App.tsx`, which also holds the splash screen with `expo-splash-screen` until fonts are ready) plus `NO_PHOTO_EMOJI` (🍽️, a placeholder pending a real cuisine-icon set). `src/components/Wordmark.tsx` renders the "Tambo." wordmark (Fraunces, terracotta-dot) reused on `AuthScreen` and `RecipeListScreen`. `RecipeListScreen` has a custom header (native React Navigation header hidden for this screen) with a client-side search filter and a Recettes/Collections toggle — Collections groups recipes by tag (client-side, no dedicated endpoint beyond `tags` now being returned on `GET /recipes`), sorted alphabetically, rendered as an adaptive photo mosaïque (1/2/3/4+ recipes). It also has a bottom icon bar (Collections/Profil/Partager, `Feather` icons from `@expo/vector-icons` — the project's only icon set) with Collections and Profil wired up (Profil added 2026-09-15, navigates to the new `ProfileScreen`); Partager still has no screen behind it. The recipe card in the "Recettes" grid shows only photo + title (the tag-chip row under the title was removed 2026-09-15, see `NOTES.md`) — tags/collections are still visible from the Collections tab.

**Phase 2 — Instagram import (slice 1, 2026-09-10)**: no native OS share-intent yet (that's slice 2 — needs `expo-share-intent` and a dev client build, since it requires native code Expo Go can't run). For now the entry point is manual: `RecipeListScreen`'s "+" button offers "Nouvelle recette" / "Importer depuis Instagram" (`Alert.alert`), the latter opening `ImportScreen` where the user pastes a post URL. `apps/api/src/lib/instagramScraper.ts` does best-effort, unofficial scraping via `POST /imports/scrape`, which always replies `200` with `scraped: boolean` rather than erroring, since a failed scrape is an expected case the UI falls back on (edit the caption / add a photo manually). Uses a headless browser (`puppeteer-core`, pointed at whatever Chromium-based browser is already installed — `PUPPETEER_EXECUTABLE_PATH` env var, or auto-detected per-OS default paths — rather than bundling a Chromium download) instead of a plain `fetch`: testing on 2026-09-10/11 showed Instagram serves an empty app shell (no `og:description`/`og:image`, no embedded caption JSON) to non-browser requests, on both Reels and photo posts, but a real (even headless) browser gets the actual JS-hydrated page. Dismisses the cookie-consent banner and any caption "...more" truncation toggle, then reads the caption from the longest text match on a known-fragile atomic CSS selector (`span.x1lliihq.x1plvlek` — several short UI strings share the same classes, hence picking the longest rather than the first) and the post image from the first sufficiently-large `<img>` served off Instagram's CDN. Fragile by design, accepted risk, see `CONCEPTION.md` §1 — the manual fallback (edit caption / add photo) stays as the safety net. `apps/api/src/lib/claude.ts` wraps `@anthropic-ai/sdk` (`ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` env vars, default model `claude-sonnet-5`) and structures a recipe from caption text and/or a photo using a **forced tool call** (`tool_choice: { type: 'tool', name: 'record_recipe' }`, `strict: true`) rather than free-text JSON parsing, for reliable structured output — exposed via `POST /imports/structure`. `ImportScreen` sends whatever caption/photo it has (scraped or manually entered) to that endpoint, then routes to `RecipeEditScreen` with `route.params.draft` (the structured recipe) and `route.params.source` (the pasted URL) pre-filling the form — same screen used for manual create, just with a non-empty starting snapshot for the unsaved-changes guard (`RecipeEditScreen`'s `beforeRemove` listener, prompts to save/discard when leaving with pending changes). Video posts (Reels): no fetchable thumbnail exists on the Reel's own page (the video streams from a `blob:` URL), and no single captured frame is reliably "the cover" (the start can be mid-scene since Reels autoplay near-instantly; later frames sometimes land on a reveal shot of the finished dish and sometimes on on-video text baked in by the poster's own editing). A profile-grid cover lookup (scrolling the author's Reels grid to find the real curated cover) was prototyped 2026-09-11 but shelved — too slow and not reliable enough when the post is far back in the grid, see `NOTES.md`. Instead (2026-09-14), `instagramScraper.ts` captures candidate frames via `<video>` + `<canvas>` (0% and 98% of the video's duration, `VIDEO_FRAME_TARGETS` — seeking straight to a late timestamp finds no buffered data and silently returns the same frame as 0%, since a Reel's player buffers around the current playhead rather than an arbitrary seek target, so the 98% capture instead mutes the video and plays forward at 16x until it reaches that point) and `POST /imports/scrape` returns them as `photoCandidates`. Rather than picking here, `ImportScreen` carries `photoCandidates` straight through to `RecipeEditScreen` (`route.params.photoCandidates`), which shows them as tappable thumbnails in its own Photo section so the **user** picks the one that actually looks like the dish right where they're already reviewing/editing the rest of the recipe — consistent with keeping recipe organization (and now cover selection) user-driven rather than AI-decided. `saveBase64PhotoToFile` (`apps/mobile/src/lib/photo.ts`) is the shared helper both screens use to turn a base64 photo/candidate into the real `file://` uri the multipart upload needs. No video/audio processing beyond those frames (transcription is a separate, later increment per `CONCEPTION.md` §6). **Collections stay user-controlled, tag = collection** (decided 2026-09-14, refined same day — see `NOTES.md`): a collection is deliberately named by the user, like naming a photo album, not generated by the AI. `claude.ts` still receives the user's existing tags as context and prefers reusing them, but the mobile side enforces the actual rule — `RecipeEditScreen` waits for `GET /tags` to load, then pre-selects only draft tags that match the user's existing vocabulary (reusing isn't creating); a genuinely new tag Claude proposes is silently dropped rather than offered as a one-tap suggestion, since even an AI-originated suggestion isn't how a collection should get its name. At least one collection is now **required** to save a recipe (enforced both in `RecipeEditScreen`'s `handleSave` and server-side via `tagsSchema.min(1)` in `recipes.ts`) — typing a name that doesn't exist yet still creates it via the existing find-or-create upsert, exactly as before. Collections are also manageable independently of any recipe: `POST /tags` (create/find-or-create standalone) and `DELETE /tags/:id` (cascades to `RecipeTag` rows only — the recipes themselves are untouched, like removing an album doesn't delete its photos) back collection creation/deletion on `RecipeListScreen`'s Collections tab (reworked 2026-09-15, see `NOTES.md` — the earlier "Gérer les collections" toggle is gone: creation is now a "Nouvelle collection" option in the "+" button's menu, deletion a trash icon next to the "Collection : X ✕" chip shown once inside a filtered collection), which now sources its list from `GET /tags` (every collection, including ones with zero recipes yet) rather than deriving it purely from recipes' embedded tag names.

**Known Expo SDK 57 gotcha**: Expo replaces the global `fetch`/`FormData` with its own WinterCG-flavored implementation by default, which does not support React Native's classic `{ uri, name, type }` FormData file part (throws `"Unsupported FormDataPart implementation"`). `apps/mobile/.env`/`.env.example` set `EXPO_PUBLIC_USE_RN_FETCH=1` to fall back to React Native's built-in `fetch`, which does support it. After changing this var, restart with `npx expo start -c` (cache clear) and do a full reload on device — a plain restart or fast refresh isn't enough since the env value is inlined at bundle time.

**Env files**: each app has its own `.env.example` (`apps/api`, `apps/mobile`) plus a root one for `docker-compose.yml`. Copy to `.env` locally; none of the `.env` files are committed. `apps/api/.env` needs `ANTHROPIC_API_KEY` (from [console.anthropic.com](https://console.anthropic.com), pay-as-you-go — separate product from a Claude.ai subscription) for the Phase 2 import endpoints to work; everything else works without it.
