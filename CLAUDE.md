## Repo structure

npm workspaces monorepo:

```
apps/api/       Fastify + TypeScript + Prisma backend
apps/mobile/    Expo + TypeScript + React Navigation mobile app
```

The two apps share no code today (no `packages/` in use yet) beyond the root `npm install`.

## Commands

Run from the repo root unless noted.

```bash
npm install                       # installs both workspaces
docker compose up -d              # starts postgres (:5432) + minio (:9000/:9001) — required before running the API
npm run dev:api                   # starts the API (tsx watch) on :3000
npm run dev:mobile                # starts Expo (Metro) for the mobile app
```

Prisma (run from `apps/api`, or via the root scripts):

```bash
npx prisma migrate dev --name <name>   # create + apply a migration after editing schema.prisma
npx prisma generate                    # regenerate the Prisma Client (also runs automatically after migrate)
npx prisma studio                      # inspect the DB visually
```

Typecheck (no test suite exists yet in either app):

```bash
cd apps/api && npx tsc --noEmit
cd apps/mobile && npx tsc --noEmit
```

Instagram import smoke test (hits Instagram for real — checks the scraper still works on 6 reference posts; run it when public posts start landing on the "restricted or deleted" manual form):

```bash
npm run check:instagram
```

Claude structuring benchmark (⚠ calls the Claude API for real, ~$0.30 per run on `ANTHROPIC_API_KEY` — 3 reference posts × 4 model/photo configurations × 2 runs; timings printed, drafts written to the gitignored `apps/api/scripts/bench-structure-results.json` for a side-by-side quality check):

```bash
npm run bench:structure
```

Health check once the API is running:

```bash
curl http://localhost:3000/health      # liveness only
curl http://localhost:3000/health/db   # round-trips through Prisma to confirm DB connectivity
```

## Architecture

**Request flow**: mobile app → HTTP/JSON → Fastify API → Prisma Client → PostgreSQL. Postgres and MinIO run in Docker (`docker-compose.yml`); the API and mobile app run directly on the host (not containerized) for fast reload during dev — there is no Docker image for the API yet, that's a deployment-time concern (`caddy` + prod compose file, not yet created).

**`apps/api`**: `src/server.ts` boots a Fastify instance (`src/app.ts`) on `0.0.0.0` (not just `localhost`, so a physical phone on the LAN can reach it). Routes are registered as Fastify plugins under `src/routes/`: `health.ts`, `auth.ts` (`POST /auth/register`, `POST /auth/login`, `GET /auth/me`, backed by `@fastify/jwt` + `bcryptjs`), `recipes.ts` (full CRUD, scoped to `req.user.userId` on every query, plus `GET/POST /tags` and `DELETE /tags/:id` for the user's own collections — see the Phase 2 paragraph below), `imports.ts` (Phase 2 — see below). `src/lib/prisma.ts` exports a single shared `PrismaClient` instance. `@fastify/cors` is registered with `origin: true` — required because Expo's web target and any browser-based testing hit the API cross-origin; native Expo Go/device builds aren't subject to CORS but the plugin is harmless for them. `@fastify/multipart` (`attachFieldsToBody: true`) parses recipe create/update requests, which are sent as multipart so a photo can ride along with the JSON-ish fields; `src/lib/minio.ts` uploads that photo to MinIO and recipes are served back through an authenticated proxy endpoint (`GET /recipes/:id/photo`) rather than exposing MinIO URLs directly.

**Prisma schema** (`apps/api/prisma/schema.prisma`): six models — `User`, `Recipe`, `Ingredient`, `RecipeIngredient` (join table with a free-text `quantity`, e.g. `"200g"`, plus a nullable `section`, e.g. `"Pour la pâte"` — lets the same ingredient appear more than once in a recipe with a different quantity per part, added 2026-09-11 after a real recipe with butter in both the dough and the cream crashed the save; unique on `(recipeId, ingredientId, section)`, with app-level dedup in `recipes.ts` as the real guard since Postgres treats two `NULL` sections as distinct; plus an `Int position` (added 2026-09-29, migration `20260929120000_add_recipe_ingredient_position`) = the ingredient's index in the submitted list, which `recipes.ts` writes on create/update and sorts by on read — before it, rows came back in arbitrary DB order, shuffling ingredients and interleaving sections; rows saved earlier all have `0`. On mobile, `groupBySection` (`src/lib/ingredients.ts`) gathers each section's items together — used for rendering on `RecipeDetailScreen` and on load in `RecipeEditScreen` — so a section title shows only once even for those older rows), `Tag`, `RecipeTag` (join table). `Recipe.steps` is a `Json` array of strings rather than a normalized steps table — deliberately minimal, revisit only if step-level metadata is needed. `Recipe.photoKey` stores the MinIO object key (nullable). `Recipe.source` (nullable free-text string, added 2026-09-10) records where a recipe came from — an Instagram/web link, a book, a person's name — deliberately untyped (no enum); the mobile detail screen renders it, when it looks like a URL, as a tappable "Voir la recette originale" chip (icon + label, `sourceLinkRow` in `RecipeDetailScreen.tsx`, added 2026-09-18) rather than the raw URL — a plain non-URL source (book, person) still renders as plain text. `Recipe.favorite` (boolean, added 2026-09-30, migration `20260930120000_add_recipe_favorite`) backs the Favoris tab. `Recipe.visibility` (`PRIVATE`/`PUBLIC`, default `PRIVATE`) exists now to support Phase 4 social sharing without a later migration. Account model is single-user (mono-utilisateur) — no group/family table. `Ingredient` and `Tag` each carry a `normalized` column (distinct from the display `name`) so find-or-create on recipe save is case-insensitive (`normalizeWord` in `recipes.ts`: `trim().toLowerCase()`) — added in migration `20260908104606_normalize_ingredient_tag_names` after duplicate rows showed up for things like "tomate"/"Tomate". It was briefly also plural-insensitive (stripping a trailing "s"), but that was dropped 2026-09-10: singular/plural carries real meaning (quantity agreement, e.g. "1 tomate" vs "4 tomates"), so "tomate" and "tomates" are now kept as distinct rows on purpose. Both models also carry a `userId` (FK to `User`, `onDelete: Cascade`) — added 2026-09-10 (migration `20260910120000_scope_ingredients_tags_by_user`) after testing with a second account showed the vocabulary was global across every user rather than private per account; the unique constraint is now `(userId, normalized)` rather than `normalized` alone, and the find-or-create upserts in `recipes.ts` key on that compound field (`userId_normalized`).

**`apps/mobile`**: `App.tsx` renders `src/navigation/RootNavigator.tsx` (React Navigation native-stack) with screens — `AuthScreen`, `RecipeListScreen`, `RecipeDetailScreen`, `RecipeEditScreen`, `ImportScreen`, `ProfileScreen` (added 2026-09-15, minimal — account email + logout, see `NOTES.md`) — all wired to the API, not stubs. `src/context/AuthContext.tsx` holds the JWT and persists it via `src/lib/storage.ts` (`expo-secure-store`, falling back to `localStorage` on the web build). `src/lib/api.ts` wraps `fetch` against `EXPO_PUBLIC_API_URL` (must be the dev machine's LAN IP when testing on a physical device — `localhost` from a phone means the phone itself) and builds multipart `FormData` for recipe create/update. Photo capture/selection in `RecipeEditScreen` goes through `expo-image-picker` (camera + library choice), whose iOS/Android permission strings are declared via the `expo-image-picker` config plugin in `app.json`. `metro.config.js` extends Metro's `watchFolders`/`resolver.nodeModulesPaths` to the monorepo root — required for Metro to resolve npm-workspaces-hoisted dependencies; without it the bundler can't find packages hoisted above `apps/mobile/node_modules`.

**Visual identity ("Tambo", "blanc éditorial" direction since 2026-09-30)**: the app's working name is **Tambo** (displayed in-app only — `app.json` name/slug, `package.json`, and the repo name are still `recipehub`/unchanged, a deliberate scoping decision from 2026-09-10). The 2026-09-30 redesign (reference + mockups from Clémentine, summarized in `NOTES.md` "Refonte design") replaced the cream direction: white background, near-black ink, structure from 1px hairlines and white space rather than bordered/shadowed cards, terracotta as an accent only (small labels, step numbers, active tab, the + button). `src/lib/theme.ts` holds the tokens (`ink`, `surface`, `hairline`, `text2`, `terracotta`, `terracottaText` — used for small uppercase labels, where `terracotta` is too low-contrast — and `green`, reserved for veggie covers), radii, fonts (`fonts.serif*` → Fraunces, titles in `serifSemiBold`; `fonts.sans*` → Inter, back from Urbanist on 2026-09-30; loaded via `@expo-google-fonts/{fraunces,inter}` and `useFonts` in `App.tsx`, which holds the splash screen until fonts are ready) and the shared `labelText` style (Inter 700, 11px, uppercase, spaced). No emoji anywhere. **Recipes without a photo** get a colored cover (`src/components/RecipeCover.tsx`): a flat color + a thin white `MaterialCommunityIcons` glyph, picked at render time from the recipe's tags (accent/case-insensitive stems; sweet → terracotta, veggie → green, else ink; `coverFor`) — no DB field; used on cards, the featured card, collection mosaics and the detail header. `src/components/Wordmark.tsx` renders the "Tambo." wordmark (Fraunces 700, terracotta dot; 36 on `AuthScreen`, 22 on `RecipeListScreen`). `RecipeListScreen` (native header hidden): top bar with the wordmark + a round search button that unfolds a search field (matches titles and collection names, accent- and case-insensitive via `matchesSearch` in `src/lib/text.ts` — "gat" finds "Gâteau"; searching by ingredient is a deferred idea), "Mes recettes" title (Fraunces 40) + "N recettes · N collections" counter, text tabs Recettes · Collections · Favoris (active = ink + 2px terracotta underline). The Recettes tab shows the newest recipe large ("Ajoutée récemment", taken out of the grid below; labelled "Importée d'une photo" when it has neither photo nor source — an approximation), then a 2-column grid of borderless cards: photo/cover 128px, "FIRST TAG · TOTAL MIN" label, Fraunces 17 title (2 lines max) — sorted alphabetically like collections. Favoris filters on `Recipe.favorite`. Collections are listed from `GET /tags` (empty ones too), alphabetically, as an adaptive photo mosaic (1/2/3/4+ recipes, covers for recipes without a photo) + name + count; no chapter numbers anymore. The bottom nav is a shared `src/components/BottomNav.tsx` (`active: 'recipes' | 'profile'`) on both `RecipeListScreen` and `ProfileScreen`: Recettes icon · round terracotta + (56px, centered) · Profil icon, icons only, active one filled in ink. "Partager" was removed until Phase 4. The + opens the "Ajouter une recette" bottom sheet (`src/components/AddRecipeSheet.tsx`, an RN `Modal` with its own slide/fade animation; also on `ProfileScreen`): Depuis Instagram · Depuis des photos · Écrire moi-même, plus "Recettes existantes" on top inside an open collection; `openAddChoice` (`src/lib/addMenu.ts`) does the navigation, passing the open collection as `presetTag`. Collections are created from a dashed "+ Nouvelle collection" tile at the end of the Collections grid (no longer from the + menu, 2026-10-01). `ProfileScreen` is treated as a tab-like destination, not a pushed screen — no back button, no swipe-back, no transition animation (`RootNavigator.tsx`), and its Recettes icon returns via `navigation.popTo('RecipeList')`. `RecipeDetailScreen` has no native header: a full-width 400px photo, or a 360px `RecipeCover` with the tags and a white Fraunces 42 title on it; round white buttons over it — back, heart (favorite, `PATCH /recipes/:id/favorite`) or, without a photo, a camera button that adds a dish photo straight away (rebuilds the full `PUT` input with `recipeInputFrom`), and "…" (Modifier / Supprimer, + favorite when there's no photo). Then tags as a label + a "Source" link, a Prépa · Cuisson · Parts block between hairlines, ingredients as quantity | name | checkbox rows (ticks are local state only), and steps numbered in terracotta Fraunces. Auth and profile screens only switched to the new tokens so far — not redesigned yet.

**Import flow (redesigned 2026-10-01, mockups in `NOTES.md`)**: shared form pieces live in `src/components/ui.tsx` (`RoundButton`, `ScreenHeading` — terracotta kicker + Fraunces 34 title + intro, `FieldLabel`, `BottomActionBar` — the fixed black pill, `SecondaryButton`, `SmallPillButton`, `InfoNote`, `DashedTile`); `Import`, `PhotoImport` and `RecipeEdit` hide the native header. `ImportScreen` has three phases: `link` (underlined URL field + "Coller" via `expo-clipboard`, local check with the same shortcode pattern as the API → "Lien Instagram reconnu" or a warning; "Pas de lien ?" goes straight to the manual phase), `waiting`, and `manual` (the fallback: a per-cause title/explanation from `NOTICES`, "Ouvrir le post" / "Réessayer", then — when a valid link was entered — "Importer des captures de la légende" first, then the caption box ("Ou colle la légende"), optional photo tile, "Mettre en forme avec l'IA"). Instagram doesn't let you copy a caption (found on device 2026-10-06), so screenshots are the main fallback: the tile pushes `PhotoImport` with `source` = the post URL, which switches that screen to a library-only "Depuis des captures" mode (no camera — screenshots live in the library) and passes the link on as the recipe's source. The waiting screen is `src/components/ImportProgress.tsx`, shared with `PhotoImportScreen`: a terracotta progress bar easing towards ~80% at the expected duration, a time-driven checklist (`ProgressStep[]`, `useElapsed` in `src/lib/progress.ts`; the last step is only "done" by the real answer), a preview block (the first page for a photo import; empty surface for Instagram, whose photo only arrives with the draft — a two-call import that would show it early is a deferred idea) and "Annuler", which aborts the call through the `signal` param of `importInstagram`/`importPhotos`/`structureRecipe` (the server still finishes its Claude call). Swipe-back is disabled while waiting. The share-intent hint from the mockup is hidden until slice 2. `RecipeEditScreen` serves create, edit and import review: a custom top bar (close + "Relecture"/"Nouvelle recette"/"Modifier la recette"), a "mise en forme par l'IA" note when `route.params.fromAi`, the photo with carousel thumbnails (terracotta ring on the chosen one, a "+" thumb for one's own photo) or a dashed "Ajouter une photo du plat" tile, collections as chips (the comma-separated text field is gone; "+ Nouvelle" opens a name field, the only way to create a collection there), Fraunces time fields, quantity | name | ✕ ingredient rows (sections still editable), terracotta step numbers, the source at the bottom. Saving a **new** recipe resets the stack to `RecipeList` › `RecipeDetail` (reusing the existing `RecipeList` route key so it stays mounted with its open collection/tab) — back from a new recipe never lands on an import screen; an edit goes back. An unsaved draft (`route.params.draft`, AI-structured or prefilled) counts as dirty even untouched, so leaving the review asks "Quitter sans enregistrer ?" (quit / save / keep reviewing) — before 2026-10-06 a photo import's result could be lost silently.

**Collection membership management (`RecipeListScreen`, 2026-09-18)**: opening an empty collection shows "Cette collection est vide pour l'instant." plus an "Ajouter une recette" CTA that opens `RecipeEdit` with the collection already selected (same draft-prefill mechanism the Instagram import flow uses). Once a collection is open (empty or not), the bottom nav's "+" (and that CTA) opens the add sheet with an extra "Recettes existantes" row on top (a multi-select picker — tap to check/uncheck, header "Terminé" button batch-applies the tag via `getRecipe` + `updateRecipe` per recipe, since `PUT /recipes/:id` has no partial-update mode — filterable via the screen's existing search bar), and the other choices carry the collection along — Instagram and photo imports via a `presetTag` route param, merged into whatever tags the structuring or manual fallback produces, "Écrire moi-même" via a prefilled draft. A collection also has its own "edit mode" (list icon next to the rename/delete icons, hidden when the collection is empty): each card gets a small remove badge (`handleRemoveFromCollection`) that un-tags the recipe immediately on tap, deliberately no multi-select step since removing from a collection doesn't touch the recipe itself.

**Phase 2 — Instagram import (slice 1, 2026-09-10)**: no native OS share-intent yet (that's slice 2 — needs `expo-share-intent` and a dev client build, since it requires native code Expo Go can't run). For now the entry point is manual: the "+" add sheet's "Depuis Instagram" opens `ImportScreen`, where the user pastes a post URL. `POST /imports/instagram` (2026-09-29, replaced `POST /imports/scrape` + a second structuring call from the phone) does the whole import server-side in one call: scrape with `apps/api/src/lib/instagramScraper.ts`, then structure with Claude — so the post's photo no longer travels server → phone → server as base64 just for Claude. It always replies `200` with `scraped: boolean` (+ `draft`, null if Claude failed — caption/photo are still returned for a manual retry) rather than erroring, since a failed scrape is an expected case the UI falls back on (edit the caption / add a photo manually). The photo is only sent to Claude when the caption is under 150 characters (`CAPTION_ENOUGH_CHARS`): a cover shows the dish, not the recipe, and measured with `npm run bench:structure` it barely changed the drafts while adding ~0.4s and 35-60% more input tokens. Scraping itself is best-effort and unofficial. **Since 2026-09-29 it's a plain `fetch` + the post's embedded JSON — no headless browser** (full history, measurements and the decisions in between in `NOTES.md`, last Phase 2 items): fetches the post page (URL cleaned down to its shortcode, dropping share-tracking params like `?stkn=`) with full browser navigation headers (`Accept`, `Accept-Language`, `Sec-Fetch-*` — with a User-Agent alone Instagram omits the post data, which is why the original 2026-09-10 plain-fetch version failed and a headless browser was used 2026-09-11 → 2026-09-29), then reads the post straight out of the JSON Instagram embeds in the initial HTML (`<script type="application/json">` blocks): finds the media object whose `code` is the URL's shortcode, takes `caption.text` (author's text with line breaks, no username/date prefix), the largest `image_versions2` candidate (a Reel's real author-chosen cover) or every `carousel_media` image (max 10), downloaded right away (signed, expiring URLs). ~1-1.5s. Returns `{ ok: true, post }` or `{ ok: false, reason }` (`bad-url`/`http-error`/`unavailable`/`no-image`). `unavailable` = the page came back without the post's data: a restricted post (author-limited or age-gated, only shown to logged-in users), a deleted post and an Instagram page change are indistinguishable from a plain fetch (verified 2026-09-29), so the route replies `scraped: false, reason: 'unavailable'` (other failures: `'bad-url'` for a non-Instagram link, `'failed'` for network/timeout/image issues). `ImportScreen` turns each case — plus a 400 "Lien invalide" and an unreachable server, told apart via the exported `ApiError` — into its own title + explanation (`NOTICES`, shown on the manual-fallback phase), e.g. "On n'a pas pu lire ce post" → paste the caption by hand (2026-09-29, replaced a single unexplained "Récupération automatique impossible"). `POST /imports/structure` is the manual path (user-entered caption and/or photo — the photo is always sent there, it may be the recipe itself, e.g. a cookbook page) and has a 10 MB `bodyLimit` (Fastify's 1 MB default rejected a full-resolution photo with a 413). `puppeteer-core`, the Chromium dependency and the video-frame capture were removed on 2026-09-29 (the browser had only been kept to word the restricted-post message more precisely). `npm run check:instagram` (`apps/api/scripts/check-instagram.ts`) runs the scraper on 6 reference posts — the only way to tell an Instagram page change from restricted/deleted posts. Fragile by design, accepted risk, see `CONCEPTION.md` §1 — the manual fallback (edit caption / add photo) stays as the safety net. `apps/api/src/lib/claude.ts` wraps `@anthropic-ai/sdk` (`ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` env vars, default model `claude-sonnet-5`) and structures a recipe from caption text and/or a photo using a **forced tool call** (`tool_choice: { type: 'tool', name: 'record_recipe' }`, `strict: true`) rather than free-text JSON parsing, for reliable structured output — used by both `POST /imports/instagram` and `POST /imports/structure`; it logs every call (`[claude] <model>: <ms>, input/output tokens, photo sent or not`) — latency is dominated by output length (700-1,000 tokens, the whole recipe rewritten), and Sonnet 5 was kept over Haiku 4.5 on 2026-09-29 for fidelity (Haiku was ~1.7s faster but dropped units and invented a prep time; results in `NOTES.md`). While waiting, `ImportScreen` shows the `ImportProgress` waiting screen (see the Import flow paragraph) — its checklist is time-based on measured phase durations, since a single server call can't report its real phase (2026-09-29). `ImportScreen` gets the draft from the import call (or, on the manual path, from `/imports/structure`), then routes to `RecipeEditScreen` with `route.params.draft` (the structured recipe) and `route.params.source` (the pasted URL) pre-filling the form — same screen used for manual create, just with a non-empty starting snapshot for the unsaved-changes guard (`RecipeEditScreen`'s `usePreventRemove`, prompts to save/discard when leaving with pending changes). Photos in the scrape response: `photo` (always set on success) is the default recipe photo — single photo, a Reel's cover, or a carousel's first image; `photoCandidates` are a carousel's images. `ImportScreen` carries both through to `RecipeEditScreen` (`route.params.photo`/`photoCandidates`), which preselects the photo and shows the carousel images as thumbnails under it — the **user** picks, consistent with keeping recipe organization (and cover selection) user-driven rather than AI-decided. (Before 2026-09-29, Reels had no fetchable cover in the rendered page, so frames captured at 0% and 98% of the video were offered instead — see `NOTES.md` for that history.) `saveBase64PhotoToFile` (`apps/mobile/src/lib/photo.ts`) is the shared helper both screens use to turn a base64 photo/candidate into the real `file://` uri the multipart upload needs. No video/audio processing (transcription is a separate, later increment per `CONCEPTION.md` §6 — the scraper already sees the Reel's direct MP4 URL in `video_versions`, logged but unused for now, which will make that simpler). **Collections stay user-controlled, tag = collection** (decided 2026-09-14, refined same day — see `NOTES.md`): a collection is deliberately named by the user, like naming a photo album, not generated by the AI. `claude.ts` still receives the user's existing tags as context and prefers reusing them, but the mobile side enforces the actual rule — `RecipeEditScreen` waits for `GET /tags` to load, then pre-selects only draft tags that match the user's existing vocabulary (reusing isn't creating); a genuinely new tag Claude proposes is silently dropped rather than offered as a one-tap suggestion, since even an AI-originated suggestion isn't how a collection should get its name. At least one collection is now **required** to save a recipe (enforced both in `RecipeEditScreen`'s `handleSave` and server-side via `tagsSchema.min(1)` in `recipes.ts`) — typing a name that doesn't exist yet still creates it via the existing find-or-create upsert, exactly as before. Collections are also manageable independently of any recipe: `POST /tags` (create/find-or-create standalone) and `DELETE /tags/:id` (cascades to `RecipeTag` rows only — the recipes themselves are untouched, like removing an album doesn't delete its photos) back collection creation/deletion on `RecipeListScreen`'s Collections tab (reworked 2026-09-15, see `NOTES.md` — the earlier "Gérer les collections" toggle is gone: creation is now the dashed "+ Nouvelle collection" tile at the end of the grid — it was a "+" menu option until 2026-10-01 — deletion a trash icon on the counter line under an open collection's title), which now sources its list from `GET /tags` (every collection, including ones with zero recipes yet) rather than deriving it purely from recipes' embedded tag names. Membership in an existing collection is also user-managed after the fact — adding recipes to one (existing-recipe picker, Instagram import with a preset tag, or a fresh recipe) and removing them (per-card badge in the collection's edit mode) — see the Collection membership management paragraph above.

**Phase 3 — photo import (2026-09-30)**: photograph a recipe (cookbook page, magazine, handwritten card) and let Claude structure it. `PhotoImportScreen` (reached from the add sheet's "Depuis des photos", with the same `presetTag` route param as `ImportScreen` when a collection is open) collects **1 to 5 photos** — camera one page at a time, or a multi-select library pick (`orderedSelection`, pages in tap order) — shown as numbered, removable thumbnails. Each photo is resized to ≤1568px on its long edge (what Claude scales down to anyway) with `expo-image-manipulator` (`preparePhotoForAi` in `src/lib/photo.ts`) before being sent as base64 to `POST /imports/photos` (`bodyLimit` 20 MB), which calls `structureRecipe` once with every photo — `structureRecipe` takes a `photos` array (Instagram import and `/imports/structure` pass at most one), and with several it tells Claude they're the successive pages of one recipe. **The photos only feed the AI** (Clémentine's decision): the draft goes to `RecipeEditScreen` without a photo, so the recipe shows a colored cover until the user adds a dish photo (camera button on the detail screen). No cropping. The same screen also takes Instagram caption screenshots (`source` param, see the Import flow paragraph). Waiting uses the shared `ImportProgress` screen (`PHOTO_STEPS`, first page as preview); its timings are estimates (one page measured at ~9s).

**Known Expo SDK 57 gotcha**: Expo replaces the global `fetch`/`FormData` with its own WinterCG-flavored implementation by default, which does not support React Native's classic `{ uri, name, type }` FormData file part (throws `"Unsupported FormDataPart implementation"`). `apps/mobile/.env`/`.env.example` set `EXPO_PUBLIC_USE_RN_FETCH=1` to fall back to React Native's built-in `fetch`, which does support it. After changing this var, restart with `npx expo start -c` (cache clear) and do a full reload on device — a plain restart or fast refresh isn't enough since the env value is inlined at bundle time.

**Env files**: each app has its own `.env.example` (`apps/api`, `apps/mobile`) plus a root one for `docker-compose.yml`. Copy to `.env` locally; none of the `.env` files are committed. `apps/api/.env` needs `ANTHROPIC_API_KEY` (from [console.anthropic.com](https://console.anthropic.com), pay-as-you-go — separate product from a Claude.ai subscription) for the Phase 2 import endpoints to work; everything else works without it.
